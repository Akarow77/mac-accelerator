## Physical link and bulk throughput

IORegistry reported the comma Linux USB Gadget at **5,000,000,000 bits/s**.
This is negotiated link speed, not application throughput. The NCM interface's
`100baseTX` media label also does not describe measured USB throughput.

- USB IPv6 link-local ping, 20 requests: 0% loss; min/mean/max
  **0.943 / 1.485 / 1.922ms** (stddev 0.220ms).
- Single-stream TCP iperf3, 5 seconds, 3X → Mac: **470Mbps receiver**, zero
  sender retransmissions reported.
- Reverse direction, 5 seconds, Mac → 3X: **676Mbps receiver**, 681Mbps sender,
  **230 sender retransmissions**, mostly in the first interval. This needs
  repeat investigation; it is not evidence of sustained reliability or a
  diagnosed cable fault.

Each temporary iperf server was scoped to the USB link-local interface, accepted
one client and exited. Neither direction was measured concurrently with RTT.

## Input-sized request/result round trip

Tool: `tools/probe_usb_roundtrip.py`. A stdlib-only client executes through ADB;
its data connection is direct IPv6 TCP over NCM, **not an ADB tunnel**. There are
no device file writes. It checks offroad state, uses bounded timeouts and one
USB-scoped listener, validates sequence/content, and closes after 120 frames.

Each request is 393,264 bytes; each response is 36,960 bytes. These are synthetic
zero-filled buffers with a sequence number, no compression. This is **raw TCP**,
not the accelerator's authenticated wire protocol: no HMAC/CRC/framing, model,
camera, preprocessing or recurrent state. Response length approximates the
authenticated result size; the actual authenticated request has additional
metadata/tag/framing. The RTT includes socket transfer, scheduling and server
content checking, not just physical-wire time; it ends at full response receipt.

20 warmup frames + 100 measured per block. Requests are paced no faster than
one per 50ms; this is not an absolute-schedule deadline qualification.
Buffers are preallocated. Socket TCP_NODELAY is enabled for both endpoints.

| Block | Requested socket buffers | Mean ms | Median ms | p99 nearest rank ms | Max ms |
| --- | --- | ---: | ---: | ---: | ---: |
| A1 | OS defaults | 16.664 | 15.739 | 26.786 | 29.543 |
| B1 | Existing app's 2MiB options | 16.208 | 15.172 | 22.404 | 22.588 |
| B2 | Existing app's 2MiB options | 16.323 | 15.519 | 22.108 | 23.101 |
| A2 | OS defaults | 16.040 | 14.927 | 23.309 | 26.181 |

All four blocks completed with zero measured RTTs over 50ms. This excludes all
model/camera work, so it is **not a 20Hz inference pass**. ABBA block means do
not demonstrate a meaningful mean-latency improvement from the buffer setting.
The earlier localhost sub-ms result did not predict physical-device RTT.

With 2MiB requested, Mac SO_RCVBUF reported 2,097,152 bytes, but device SO_SNDBUF
and SO_RCVBUF each reported 458,752 bytes (Linux accounting includes doubling).
Read-only sysctl checks showed `net.core.rmem_max` and `net.core.wmem_max` both
229,376 bytes. These limits were **not modified** and are not established as the
cause of the 16ms RTT. A2's default client send/receive values were 87,040/374,400
bytes, and the server receive value was 131,376. A1 predates buffer-value logging.

Private local reports: `artifacts/usb-raw-roundtrip-20260928-01.json` through
`-04.json`. The tool supports `--socket-buffers 0` or `2097152`; use fresh scoped
addresses and a new output filename for each run.

## Implications and next gates

At the measured 470Mbps bulk upload rate, 393,264 input bytes correspond to about
6.69ms of serialization, while a 7,471,104-byte raw NV12 camera pair corresponds
to about **127ms**. These are calculations from this short throughput run, not
measured per-frame raw-camera transfers or guaranteed bounds. Sending full raw
frames is therefore not the promising default on this measured connection.

That was an estimated raw-pair size, not the subsequently observed padded
camera allocation. The [September 29 snapshot test](CAMERA_USB_BENCH_2026-09-29.md)
found 4,804,608 bytes per camera (9,609,216 bytes for two); use those observed
sizes for the current raw-buffer transport budget.

Keep the compact, already-warped-input design while investigating capture and
transfer isolation. Do not reinsert synchronous GPU readback into modeld.
Next measure the **actual authenticated protocol** over this physical link,
then repeat with inference. Separate device preparation/readback and local-model
interference before any live-camera observer. Do not subtract historical model
benchmarks from these measurements or add them as a guaranteed end-to-end budget.

Local regression checks after adding this probe: **88 unit tests passed**, Ruff
passed for the newly edited tools/tests. This checks software helpers, not vehicle
safety. After the run, the device remained offroad, its Git tree was unchanged,
and no temporary iperf or inline probe client remained. No GitHub push or app
release was performed in this session.

## Follow-up optimization trials

Two socket-only candidates were tested in ABBA order, 100 measured frames per
block after 20 warmup frames. Same compact raw TCP payloads, no model/camera.

| Candidate | A1 mean ms | B1 mean ms | B2 mean ms | A2 mean ms |
| --- | ---: | ---: | ---: | ---: |
| Set buffers before connect/listen as well as after | 16.926 | 16.063 | 16.291 | 16.517 |
| Force larger client send buffer on this socket only | 16.188 | 16.063 | 16.397 | 16.241 |

The first candidate saved about 0.545ms in these block means, but tail behavior
did not consistently improve (B2 max 32.879ms versus A2 max 23.379ms). This is
insufficient evidence for deployment. The second did not improve mean latency,
despite Linux SO_SNDBUF increasing from 458,752 to 4,194,304 reported bytes.
`SO_SNDBUFFORCE` requires privilege and remains an explicit bench-only option;
no sysctl was changed. Neither candidate was applied to the production server
or device application. Reports are `artifacts/usb-preconnect-20260928-*.json`
and `artifacts/usb-sendbuffer-20260928-*.json`.

Additional instrumentation showed mean client `sendall()` duration around
13.7–14.6ms out of roughly 16ms RTT. This locates waiting inside the sending
call but does not distinguish CPU work, kernel queuing, USB transfer or ACKs.

An attempted CPU-affinity comparison was **not completed**. A1 mean was 15.882ms;
B1 failed its allowed-core guard before connecting. Read-only follow-up found
`/sys/devices/system/cpu/online` equal to `0-3` and allowed affinity `[0,1,2,3]`.
Earlier in the session both clusters had been online, with performance governor
and 1,689,600kHz readings. Thus the current detached/offroad measurements must
not be assumed to represent onroad CPU conditions. No cores were forced online,
no realtime priority was set and no local-model affinity was changed.

The probe now records sender call duration, effective affinity and requested
socket options. A preflight guard rejects unavailable cores before opening a
listener (the first failed trial had instead waited for the listener timeout).
The device-side guard remains in case affinity changes between checks.
Tests include embedded-client syntax and absolute receive deadlines: **90 unit
tests passed** after the preflight addition. No measurable application-level
speedup is claimed. Final device check remained offroad with manager/UI running
and a clean accelerator-branch working tree.

## Chunking and CPU/TCP profiling follow-up

An ABCCBA comparison kept the same payload and absolute two-second frame
timeout, using preallocated memoryview chunks rather than copying each chunk.
Mean RTT pairs: single send **16.191/16.451ms**, 16KiB chunks
**17.564/17.871ms**, 64KiB chunks **16.545/17.382ms**. None of 600 measured
frames exceeded 50ms; the single-send final block still had a 47.012ms maximum.
Chunking was not adopted. Reports: `artifacts/usb-chunks-20260928-*.json`.

The extended diagnostic client exceeded the legacy ADB shell command path's
capabilities. Non-PTY shell was explicitly unsupported; two stdin-based exec
attempts timed out. The working launcher now sends the same inspectable source
as a compact zlib/base64 argument through `adb exec-out`, without writing device
files. This compresses **only the diagnostic program**, not the measured TCP
payload. Failed launches are preserved as failed reports, not performance data;
no lingering stdin-waiting client was found afterward.

Successful profile `artifacts/usb-tcp-profile-20260928-r5-a1.json`, 100 measured:

- Raw application RTT mean **16.594ms**, p99 **23.824ms**, max **26.018ms**.
- Sender send-call wall mean **14.206ms**; sending thread CPU mean **11.700ms**.
- Linux TCP_INFO smoothed RTT mean **1,090us**, maximum **3,369us**; zero new
  retransmissions in the measured interval. Congestion window 62–112 segments,
  send MSS 1,428 bytes. The first 104-byte layout was checked against device tcp.h.

Thread CPU time includes user and synchronous kernel execution; it is not a
Python-only profile and does not prove a specific copy or driver is responsible.
TCP's smoothed RTT is not the full request/result RTT. These observations point
to substantial sender CPU work rather than attributing all delay to ACK waiting.

CPU 0–7 were allowed at this successful run's preflight and final snapshot.
Before the proposed 4–7-only comparison they became unavailable again; the new
preflight guard stopped that trial without opening a listener. The ABBA CPU
comparison therefore **remains incomplete**, and no high-core speedup is claimed.
No CPU online state or governor was changed by these trials. Final check showed
0–3 online, offroad=1, manager/UI running and unchanged device Git working tree.

## Authorized bounded high-core hold: positive transport result

User explicitly authorized keeping high-performance cores online for a bench
comparison. Inspection of hardwared showed power saving depends on ignition
being absent and screen brightness approaching zero; hardware.set_power_save
offlines CPUs 4–7. Thus screen state can change the previous test conditions.

`tools/hold_big_cores_bench.py` held CPUs 4–7 online for **75 seconds**, checking
offroad state and eight CPU temperature sensors every 250ms. It refuses to start
at 75°C or above and stops at that temperature. It changes neither governors,
frequency limits, realtime priorities nor Params. Original online states were
all zero; the guard reported successful restoration with no errors after expiry.
Only four online writes were needed. Initial maximum CPU temperature was 45.0°C;
peak was **48.2°C**. No permanent keep-awake setting was installed.

With all cores held online throughout, the same raw TCP probe ran ABBA:

| Client affinity | Mean RTT ms | p99 ms | Max ms | Send wall mean ms | Send CPU mean ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| Default 0–7, A1 | 20.537 | 27.506 | 27.645 | 17.853 | 14.758 |
| 4–7, B1 | 10.432 | 17.412 | 23.279 | 7.016 | 6.250 |
| 4–7, B2 | 10.326 | 13.971 | 27.529 | 6.854 | 6.236 |
| Default 0–7, A2 | 20.505 | 26.796 | 28.494 | 17.859 | 14.730 |

Equal-sized block means are **20.521ms versus 10.379ms**, about **49.4% lower
raw transport RTT** in this trial. Each block had 20 warmup + 100 measured frames;
all measured blocks had zero >50ms RTTs and zero TCP retransmissions. Reports:
`artifacts/usb-held-cores-20260928-{a1,b1,b2,a2}.json`.

This is evidence for the affinity candidate under the held-core condition, not
evidence that merely keeping cores online helps default scheduling. The historical
~16ms runs had different power/governor conditions and are not its matched
baseline. Maximum latency remains substantial. No camera, model inference,
authentication or active local-model interference was included. Reserving cores
4–7 for a sender may compete with the normal driving stack, so this has not been
applied to a live observer, to the accelerator server or as a boot-time policy.

The guard's restoration, temperature abort and no-offlining-on-onroad behavior
have simulated-sysfs tests. If the device leaves offroad during a hold, it yields
to hardwared without restoring an offline state that might disrupt onroad work.
The next validation is the real authenticated protocol with this explicitly
scoped bench affinity, followed by inference and separate interference checks.
